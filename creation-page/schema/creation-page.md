# 创作页数据格式（jc-doc）

创作页是一个单文件 HTML。页面上显示的所有内容都从文件里唯一的 jc-doc 数据块画出来；用户在页面上改的内容由保存脚本（kit）逐格写回这个数据块，其余字节不动。AI 读和改页面都只动这个数据块，并且一律通过 `brain_page.py`（和保存服务用同一把文件锁、同一套逐格规则）。

本文说明五件事：文件长什么样、jc-doc 的结构、每个字段谁写、生成和改页面的规则、保存服务的接口和来源隔离。

## 一、文件长什么样

生成脚本 `build_page.py` 把模板 `template/shell.html` 里的占位换掉，得到一个不依赖网络和 CDN 的单文件：

| 占位 | 换成什么 |
| --- | --- |
| `{{TITLE}}` | `编号 标题`，已做 HTML 转义，例如 `T001 用 AI 三分钟想好一条视频的开头`；可以出现多次 |
| `{{STYLE}}` | `template/style.css` 全文，外面一定是 `<!--jc-style:start--><style>…</style><!--jc-style:end-->` |
| `{{KIT}}` | `kit/kit.js` 全文，外面一定是 `<!--jc-kit:start--><script>…</script><!--jc-kit:end-->` |
| `{{APP}}` | `template/app.js` 全文，外面一定是 `<!--jc-app:start--><script>…</script><!--jc-app:end-->` |
| `{{DOC}}` | jc-doc 数据。写在 `<script id="jc-doc" type="application/json">…</script>` 里时只填 JSON，单独写时自动包成这个标签；包它的 script 标签必须带 `id="jc-doc"` |

`{{STYLE}}`、`{{KIT}}`、`{{APP}}` 三个占位可以单独写、写在对应标签里（保留标签属性），或者连首尾标记一起写，生成出来都是「开始标记、一个完整标签、结束标记」。`template/shell.html` 用的是连标记一起写的写法。

生成后脚本会自检：文件里 jc-doc 恰好 1 个并且能被保存服务读出来；kit、样式、界面脚本三对首尾标记各恰好 1 个、前后顺序对、中间恰好一个完整的标签；HTML 属性和样式里没有 `http://`、`https://`、`//` 开头的外部资源（参考视频的「看原片」链接放在 jc-doc 数据里，由页面画成普通链接，不算外部资源）。任何一条不满足就不写文件。

写进脚本和样式的内容里，`</script` 会转成 `<\/script`，`</style` 会转成 `<\/style`；jc-doc 里的 `<`、`>` 转成 `\u003c`、`\u003e`，所以稿子里出现 `</script>` 也不会截断页面。

**模板只有一份，旧页面自动用上新模板。** 保存服务按固定网址 `http://127.0.0.1:端口/p/<page_id>` 提供页面时，把样式、界面脚本、保存脚本这三段（三对首尾标记之间）都换成模板目录里的当前版本（`template/style.css`、`template/app.js`、`kit/kit.js`，服务启动时可以用 `--template-dir`、`--kit-dir` 换目录），并在 kit 那段前面加一行 `window.JC_SERVED = {fingerprint, path, parts}`，`parts` 写明每段用的是当前模板（`current`）还是页面自带的（`embedded`）。所以改模板不用重新生成页面，刷新就是新版。文件本身不动，换的只是这一次发给浏览器的内容。直接双击打开文件（file://）时，用的是页面文件里生成那天嵌进去的那份。

三个文件最后一行都必须是结束标记：`/* jc-kit:eof */`、`/* jc-style:eof */`、`/* jc-app:eof */`。服务靠它判断文件没写一半；某个文件读不出、不是 UTF-8 或没有这行，这一段改用页面文件里自带的那份，页面照样能打开能存，原因写进服务日志和 `/healthz`。生成脚本遇到没有结束标记的模板直接拒绝。只有 kit 标记、没有样式和界面脚本标记的老页面，服务只换 kit。

外壳 `shell.html` 本身不换，所以外壳里只放 `#app`、jc-doc 和这三段；界面元素一律由界面脚本从 jc-doc 画出来。也因为旧页面会跑新界面脚本，界面脚本读 jc-doc 必须按「只加不删」兼容：可选的键缺了按没有处理，不认识的键、字段、条目种类不报错。现在一个保存服务只配一套模板；以后有第二种页面模板时，要在标记里带模板名或按 jc-doc 的 `kind` 选模板目录，到时再改服务。

## 二、jc-doc 结构

### 页面级键

| 键 | 说明 |
| --- | --- |
| `page_id` | 页面身份号，10 位随机短码（字母表 `abcdefghijkmnpqrstuvwxyz23456789`）。第一次生成时定下，重新生成沿用。保存服务按它找文件，文件改名、挪目录都不断 |
| `content_id` | 内容编号，例如 `T001` |
| `kind` | 固定写 `创作页` |
| `schema` | 数据格式版本，现在是 `1` |
| `token` | 口令。直接双击打开文件（file://）时，保存请求必须带上它；重新生成沿用 |
| `service_origin` | 保存服务地址，file:// 打开时 kit 用它找服务。只认 `http://127.0.0.1:端口`（不能写 localhost，见第五节来源隔离）。默认是工作台设置里保存服务的端口（`ports.save`，默认 `http://127.0.0.1:18977`） |
| `items` | 条目数组，见下 |

### 条目通用结构

```json
{ "id": "seg-k3m9x2pq", "kind": "segment", "locked": { … }, "fields": { … } }
```

- `id`：条目身份号。生成一次、永不重排、不用位置编号。`build_page.py` 生成的带前缀：页面信息 `info-`、段落 `seg-`、建议 `sug-`，后面接 8 位随机短码。输入数据里给了 id 就沿用；id 只能用字母、数字、`_`、`-`，1 到 64 位，不能是纯数字（纯数字就是位置编号，AI 重排后改动会落到别的条目上）。
- `kind`：`info`（页面信息）、`segment`（段落）、`suggestion`（建议），以后加的新种类用小写英文名（例如录屏步骤 `step`）。每个条目都明确写种类，页面和命令按它认条目，不靠身份号前缀猜（只有没写 `kind` 的老数据才按前缀和键推断）。保存服务不看这个键。
- `locked`：锁定部分，AI 写，页面只读。
- `locked.ai_state`：AI 写的状态（例如对「写给 AI 的话」的回复），也是 AI 写、页面只读，但**不参与条目指纹**。
- `fields`：可改部分，页面上逐格改、逐格存回。值一律是字符串。

**只加不删**：以后长枝干只允许三种扩展，保存服务一行都不用改：

1. 给某种条目加可选的锁定键：在输入数据的段落、建议里写 `locked: {…}`，页面信息写在顶层 `info.locked` 里，参考里的额外键（例如「画面」`visual`）直接写在那条参考里；
2. 给某种条目加可选的可改字段：段落、建议里写 `fields: {…}`，页面信息写在 `info.fields` 里（例如段落的「我方画面」`our_visual`），值一律是字符串；
3. 加新的条目种类：写在输入数据顶层的 `items` 里，每条 `{id, kind, locked, fields}`，`kind` 用小写英文名（例如录屏步骤 `step`），`locked.segment` 写所属段落（段落 id 或段序号）。

不删键、不改名。生成脚本、保存服务、`brain_page.py` 读到不认识的键和种类都原样保留：保存服务逐格写回任何条目的任何字段；重新生成时按身份号保留所有可改字段；`export` 导出后原样重新生成，页面一个字节都不变。页面上还没有专门模块的扩展，由界面的兜底模块按原样列出（锁定键只显示，可改字段画成文本框，照样自动写回），`brain_page.py read` 也列在「其他格子和条目」里。这三种方式用 AI 教程假数据验证过，见 `tests/fixtures/tutorial_ext.json` 和 `tests/test_extension.py`。

**条目指纹**：`locked` 去掉 `ai_state` 这个键之后，规范化成 JSON（键排序、字符串统一换行符和 Unicode NFC、整数形式的小数写成整数、紧凑分隔符、不转义中文）算 sha256，取前 12 位。保存服务 `brain_save.item_fp` 和 kit 里的 `itemFp` 必须是同一个算法。页面提交改动时带上它；文件里这一条的指纹变了（AI 改了标题、参考、底稿等），这一格按冲突处理。AI 只写 `ai_state`（例如回复）时指纹不变，用户正在改的格子不会因此冲突。

### 页面信息（每页一个，`kind: "info"`）

| 位置 | 键 | 说明 |
| --- | --- | --- |
| locked | `type` | `口播`、`教程`、`科普` 之一。决定页面打开哪些模块 |
| locked | `stage` | `写稿`、`审稿`、`定稿`、`录制准备` 之一。顶栏阶段条只显示，由 AI 改 |
| locked | `title` | 标题 |
| locked | `narrative` | `{ "story": 讲了个什么故事, "audience": 给谁看, "problem": 解决什么问题 }` |
| locked | `speech_rate` | 每秒字数，默认 5（写成自己的语速；顶栏全稿字数悬停时显示上下 0.5 个字这个范围对应的时长）。算秒数和通读视图的开头 5 秒线。字数只数汉字、字母、数字（标点和空白不算），秒数四舍五入到整秒；页面和 `brain_page.py read` 用同一算法 |
| locked.ai_state | `handled_note`、`reply`、`replied_at` | AI 处理「整体意见」时抄下的原文、回复和时间（`brain_page.py reply --item info`） |
| fields | `overall_note` | 整体意见，用户写给 AI |
| fields | `approved` | 「内容已确认」：空，或用户点按钮时的时间（ISO 8601） |
| fields | `recorded` | 录完的定稿，用户贴进来 |
| locked | `spare_refs` | 可选。参考里有、这一稿没用上的段落，数组，每项和参考同样的键，另加 `why`（为什么没用上、想借的话怎么借）。页面在对照视图底下收成一块「参考里有、这一稿没用上的」 |

### 段落（`kind: "segment"`）

| 位置 | 键 | 说明 |
| --- | --- | --- |
| locked | `order` | 显示顺序，从 1 起。页面按它排序，不按数组位置 |
| locked | `title` | 段标题 |
| locked | `role` | 这段起什么作用（口播时显示在段标题旁） |
| locked | `refs` | 参考数组，每项 `{ "who": 谁, "source_type": "口播原话" / "简介文案" / "发布文字" / "说明", "time": 时间码, "text": 原文, "url": 看原片链接 }`，多家时上下堆叠。`说明` 类参考不是谁的原话，是一句交代（例如「她这里没有对应的原话」）：`who`、`time`、`url` 都可以不写（其余三种必须写 `who`）；页面用灰色说明样式，不显示时间和「看原片」，不算进「显示哪家」的勾选，也不参与「和我的版本连续 8 字相同」的标记；写了 `who` 显示成「参考：谁」。参考另有三个可选键（2026-09-27 教程枝干定，所有类型都认）：`role` 角色，`对标`、`补充参考`、`效果样例` 之一，显示成参考头上的小标签；`visual` 对方这段画面上是什么（文字），显示在原文下面；`video` 本地原片的位置（相对页面文件的路径，可以用 `..`），有它时「看原片」用本地原片、从 `time` 的开头播放，没有才用 `url`。其他额外的键原样保留 |
| locked | `baseline` | 底稿：AI 上次交稿时的我的版本，用来显示删改痕迹 |
| locked | `teleprompter` | 可选。写 `false` 时这一段不进「复制提词稿」 |
| locked.ai_state | `handled_note` | AI 处理「写给 AI 的话」时抄下的原文 |
| locked.ai_state | `reply` | AI 的回复 |
| locked.ai_state | `replied_at` | AI 回复的时间 |
| fields | `mine` | 我的版本，右栏只归用户 |
| fields | `note` | 写给 AI 的话（不进稿子） |

「写给 AI 的话」算不算已处理：`note` 不为空，并且和 `ai_state.handled_note` 不一样（比较前统一换行符和 NFC），就是「待处理」；一样就是「AI 已处理」，显示 `ai_state.reply`。用户在 AI 回复后再改 `note`，它自动变回「待处理」。

### 建议（`kind: "suggestion"`）

| 位置 | 键 | 说明 |
| --- | --- | --- |
| locked | `segment` | 所属段落的 id |
| locked | `category` | `表达`、`衔接`、`拗口`、`口径`、`事实` 之一 |
| locked | `source` | `AI` 或 `运营` |
| locked | `original` | 原句。新增（`build_page.py` 生成、`brain_page.py suggest`）和改原句（`brain_page.py set-locked --key original`）时都必须在所属段的 `mine` 里恰好出现一次（重叠出现也算两次） |
| locked | `reason` | 为什么改，讲人话，一句讲清（建议 60 字以内，页面默认只显示两行） |
| locked | `basis` | 依据 `{ "type": "参考口播" / "参考画面" / "你之前定的" / "AI 自己的判断" / "运营", "text": 说明 }`，页面按 type 分色，`text` 一句。「参考画面」是教程里「参考视频就是这么拍的」 |
| locked | `verdict` | 结论：`已定要改`、`待你定`、`等录屏再定`、`不用改` 之一（页面显示成需要修改、建议修改、录屏后再定、无需修改）。「等录屏再定」给要看真实运行结果才能写的句子，录制视图里会把这些句子标在所属段上 |
| fields | `proposed` | 改成。AI 先填，用户可以改（「先改再采纳」）。**空字符串表示删掉整句**，见下 |
| fields | `decision` | 空、`采纳`、`不采纳`、`部分采纳` 之一 |

采纳时页面要同时写两格（`mine` 换成改后的句子、`decision` 写「采纳」），这两格用同一个 `group` 一次提交，保存服务保证全成或全不成。原句在当前 `mine` 里找不到或不止一处时，页面把采纳按钮变灰。

**删句建议**：`proposed` 是空字符串（去掉首尾空白后为空也算）表示建议把原句整句删掉。`original` 写要删的那一整句（带句末标点），`proposed` 写 `""`。生成脚本、`suggest`、`set-field` 都接受空的「改成」，判断规则只有一处（`creation_doc.py` 的 `deletes_sentence`，和页面的判断一样）；页面卡片写「删掉这句」，采纳就从我的版本里删去原句（仍是 `mine`、`decision` 同组提交）；`brain_page.py read` 把这条的「改成」写成「删掉这句」，生成脚本汇报条数时单独数出删句的条数。

建议卡按类别筛选：每种类型默认只看哪几类写在界面脚本的「类型 → 模块」配置表里（现在只有口播配了，是衔接、拗口、口径；别的类型没配，一直显示全部）。这个默认筛选只在「审稿」阶段（以及以后的审稿视图）生效，「写稿」等阶段默认显示全部类别。用户点过类别按钮后，按阶段分别记在这台浏览器里。

### 教程枝干（`type: "教程"` 时有专门模块）

段落另带两个可改字段（写在输入数据段落的 `fields` 里；AI 先填，用户可改，AI 用 `set-field` 改不用 `--user-approved`）：

| 位置 | 键 | 说明 |
| --- | --- | --- |
| fields | `visual_type` | 画面类型，可以多选，用顿号连起来，例如 `录屏、字卡`。页面上是点选按钮，选项是 真人口播、录屏、截图、图片、AI 画面、实拍、字卡、交给剪辑（都是用户自己的叫法），表外的值照样显示 |
| fields | `our_visual` | 我方画面：这段观众看到什么，一两句 |
| fields | `todo_me` | 可选。分工里的「你录」：这段用户要录的屏。空着表示不用用户动手；以「可选」开头表示录了更好、不录也能交。段标题旁显示橙色「你要录屏」或浅橙「可选录屏」 |
| fields | `todo_editor` | 可选。分工里的「剪辑做」：剪辑在这段要找的图、做的字卡和动画。「你录」空着、这格有字时，段标题旁显示灰蓝「剪辑做」 |

录屏步骤是一种新条目（写在输入数据顶层的 `items` 里）：

| 位置 | 键 | 说明 |
| --- | --- | --- |
| 条目 | `kind` | `step` |
| locked | `segment` | 所属段落的 id（输入数据里也可以写段序号） |
| locked | `order` | 全篇录屏顺序，页面上显示成「第 N 步」 |
| locked | `where` | 在哪发、先点哪里，例如「新开一个任务；先在技能列表里选上两个技能」 |
| locked | `line` | 对应哪句口播（我的版本里的原句） |
| locked | `expect` | 发完应该看到什么 |
| locked | `caution` | 可选。录之前注意（例如画面上会露出的名字和口播对不上），页面用黄底标出 |
| fields | `prompt` | 要发送的内容，用户可以改，页面上一键复制。只能出现观众在口播里听得到的东西 |

页面：写稿、审稿阶段还是对照视图，参考下面一行对方画面，我的版本下面是画面栏，录屏步骤默认收成一行；多一个「录制」视图（到录制准备阶段、用户没点过视图时默认打开），整篇排成一栏的录屏清单，录屏步骤全部展开，「等录屏再定」的句子标在所属段上，「复制画面脚本」复制成「段、口播、画面」表格（贴进在线表格或文档就是表，给剪辑用）。复制提词稿不带提示词（提示词在录屏步骤里，不在我的版本里）。

段落写了 `todo_me` 或 `todo_editor` 时（两格至少写一格，另一格给空字符串也算），画面栏换成「分工」两格：录制视图不再显示画面类型按钮，空着的「我方画面」不再画出来；录制清单顶上多一张总表，左边「你要录的」（必录在前、可选在后，带「只看我要录的」开关），右边「剪辑做的」，点一项跳到那一段；「复制画面脚本」改成四列：段、口播、剪辑做、我录的素材。

没有专门模块的类型（例如 科普）用到这些键时，由兜底模块按原样列出，能改能存（`tests/fixtures/tutorial_ext.json` 换成 科普 类型验证）。

### 参考分析（所有类型都认）

参考两家以上时，原文堆在一起像一堵文字墙，看不出每个环节各家是怎么讲的。页面的角色是陪用户创作的编导，所以参考那一栏先给编导的功课（标得显眼的讲法点和一段分析），原文按需展开。

两种新条目，都写在输入数据顶层的 `items` 里，全部锁定（AI 写）。单独成条目、不写进段落，是因为段落的指纹按整个 `locked` 算：AI 改分析时不能让用户正在改的那段我的版本冲突。

**每段一条 `refnote`**（只给这段真有参考的段；一段只能一条）：

| 键 | 说明 |
| --- | --- |
| `segment` | 所属段落（段落 id 或段序号） |
| `summary` | 这一段参考怎么讲，两三句结论，180 字以内；最后一句落到「你这段可以怎么写」 |
| `points` | 讲法点，1 到 4 条，按对标那家的讲述顺序排。每条 `{tag, say, cover, who, quotes, over?, visual?}`：`tag` 是 引入、顺序、操作、解释、画面、定义、比喻、例子、对照、收句 之一（教程多用前五个，科普多用后五个加引入）；`say` 一句 20 到 35 字的大白话；`cover` 是 `共性`（几家都这么讲，`who` 至少两家、每家都要有原句）、`独有`（`who` 一家）、`多做`（`who` 是多做的那家，`over` 是在哪家基础上多做）；`quotes` 是原句 `[{who, time, text}]`，第一句显示成代表原句，其余用来在原文里着色 |
| `points[].visual` | 可选，`{who, time, text}`：那一秒画面上是什么（教程用） |
| `borrow` | 可以借的，最多 3 条，每条 `{type: "照用" / "超一步", text, sug?}`；`sug` 写一条建议的 id，页面上出「看对应的修改建议」，点了跳到那张卡、能一键采纳 |
| `merged` | 可选，`[{who, base, ratio}]`：这段里 who 是照着 base 改写的（中译中），ratio 是逐字相同的比例；原文那一行写「≈base，本段 X% 逐字相同，只看改动即可」 |

**全片一条 `skeleton`**：`families`（每家 `{who, role, date, stat}`，最多 4 家，中译中的两家可以并成一家写）、`relation`（几家是什么关系，一句）、`rows`（骨架的每一步，1 到 8 行，每行 `{step, segment, cells: {谁: "时间码 做了什么"}, more?: [谁]}`，`segment` 是这一步对应用户的第几段，没有写 null）、`inference`（可选，数据归因，开头写「推断」）。

生成时的硬规矩（`build_page.py` 拦截，不合格不生成）：原句必须逐字出自这一段那家的原文、60 字以内；时间必须落在那条参考的时间段里（前后放宽 3 秒）；`who` 必须是这一段参考里的名字；标签、`cover`、`type` 只能取上面的值；讲法点 1 到 4 条、可以借的最多 3 条；链接的建议必须存在。同一段两家逐字相同（连续 8 字以上）占到四成以上而没写 `merged` 时，只提醒不拒绝。

页面：这一段有两家及以上参考、又有 `refnote` 时进入分析模式：左栏先是「这一段参考怎么讲」（结论、讲法点、可以借的），下面原文按家收成一行一行（谁、角色、这段几条原文、时间段），点一家只展开这一家，原文里的关键句按讲法点的颜色标出（同色＝同一个讲法点）。只有一家参考时原文照旧直接展开，有分析就放在原文上面。`skeleton` 放在对照视图最上面，默认收成一行「几家参考的关系」，展开是一张窄表，最后一列能跳到用户的第几段。在分析里选字点「写给 AI」，批注引文写成「分析：「…」」。

### 发布文字：标题、封面文字、简介（所有类型都认）

逐字稿写完以后，标题、封面文字和简介也由 AI 先快速出几版候选，用户挑、改，最后用哪个由用户定；用户每次选了哪个、改了哪几个字，都能读回来，AI 下次就更懂用户的口味。封面图不在这里做，这里只出封面上的字。

两种新条目，都写在 `items` 里，AI 用 `brain_page.py publish` 一次放进页面（也可以写在输入数据的 `items` 里随页面生成）：

**每样一条 `pubslot`**（标题、封面文字、简介各最多一条）：

| 位置 | 键 | 说明 |
| --- | --- | --- |
| locked | `slot` | `标题`、`封面文字`、`简介` 之一 |
| locked | `refs` | 参考视频的同类文字，数组，每项 `{who, text, stat?}`：`who` 谁，`text` 对方的标题、封面上的字或简介原文，`stat` 可选的一句数据（例如「赞 6.3 万 藏 7.6 万」） |
| locked.ai_state | `handled_note`、`reply`、`replied_at` | 和段落一样，AI 处理「写给 AI 的话」时写（`brain_page.py reply --item <pubslot id>`） |
| fields | `final` | 你定的：用户最后用的那版。只归用户，AI 改要 `--user-approved` |
| fields | `note` | 写给 AI 的话，例如「标题太平，要更有冲突」，AI 按它再出一轮 |

**每个候选一条 `pubcand`**：

| 位置 | 键 | 说明 |
| --- | --- | --- |
| locked | `slot` | 属于哪一样 |
| locked | `round` | 第几轮，`publish` 自动记（同一样每调用一次加 1） |
| locked | `order` | 这一轮里的顺序 |
| locked | `angle` | 可选，角度，例如封面文字的 `判断型`、`冲突型`、`结果型` |
| locked | `reason` | 为什么这么写，一句 |
| locked | `basis` | 可选，`{type, text}`，type 是 `参考视频`、`以往数据`、`你之前定的`、`AI 自己的判断` 之一 |
| fields | `text` | 候选文字，AI 先填，用户可以直接改 |
| fields | `decision` | 空、`选用`、`不用` 之一（用户的格子） |

页面：顶栏视图按钮「标题封面简介」（有候选、还有一样没定时带黄点）。每样一张卡：最上面「你定的」一格和「复制」，下面是候选（文字能直接改，按钮「用这个」「不用」「撤销决定」），再下面收着「参考视频怎么写的」，最后是写给 AI 的话。「用这个」把候选文字写进「你定的」、这个候选记成「选用」、同一样里原来选用的那个改回空，几格同组提交；之后用户在「你定的」里接着改，读回时 AI 能看出他在候选基础上改了什么。还没有候选时，这个视图只写一段说明：勾了「内容已确认」以后 AI 会在这里出候选。

`brain_page.py read` 在「标题、封面文字、简介」一节列出：每样用户定的、选的是哪个候选、他在候选基础上的删改（CriticMarkup）、没选或标了不用的候选；页面「内容已确认」了还没有候选时，摘要开头写一行「下一步：……」。写给 AI 的话待处理时也列在「待处理的写给 AI 的话」里。

`publish` 的输入文件：

```json
{ "slots": [
  { "slot": "标题", "refs": [ { "who": "博主乙", "text": "蒸馏的保姆级教程", "stat": "赞 6.3 万 藏 7.6 万" } ],
    "candidates": [ { "text": "…", "angle": "结果型", "reason": "…", "basis": { "type": "参考视频", "text": "…" } } ] },
  { "slot": "封面文字", "candidates": [ … ] },
  { "slot": "简介", "candidates": [ … ] } ] }
```

只加不删：没有这一样就新建；给了 `refs` 就换成新的，没给就保留原来的；候选一律追加，记成新的一轮。整个文件一次写入，开着的页面只刷新一次。

## 三、谁写什么

| 字段 | 谁写 | 怎么改 |
| --- | --- | --- |
| 页面级键 | `build_page.py` | 重新生成时 `page_id`、`token` 沿用 |
| 所有 `locked`（除 `ai_state`） | AI | 输入数据加 `build_page.py`，或 `brain_page.py set-locked`、`rebase`、`suggest` |
| `locked.ai_state` | AI | `brain_page.py reply` |
| `mine`、`note`、`decision`、`overall_note`、`approved`、发布文字的 `final` | 用户 | 页面上改。AI 用 `brain_page.py set-field` 改这几格会被拒绝，除非带 `--user-approved`（用户明确同意时才加） |
| `proposed` | AI 先填，用户可以改 | 页面上改；AI 用 `set-field` 改 |
| `recorded` | 用户贴，或用户把录完的稿子交给 AI 时 AI 代贴 | 页面上改；AI 用 `set-field` 改 |
| 扩展出来的可改字段（例如 `our_visual`、`prompt`） | 用户在页面上改，AI 也能先填 | 页面上改；AI 用 `set-field` 改，暂时和 `proposed` 一样不用 `--user-approved`。做枝干时如果某格只归用户，把它加进 `creation_doc.py` 的 `OWNER_FIELDS` |

页面上只能改已有条目的 `fields`，不能增删条目；增删条目（新增建议、加段）交给 AI。

## 四、生成与改页面

### 生成：`build_page.py`

```
python3 build_page.py <数据.json> [--out <页面.html>] [--root <工作文件夹>] [--drop-missing] [--check] [--page-id <身份号>]
```

- `--check`：只校验、不写文件，通过时打印「数据合格（只校验，没写文件）：N 段，M 条建议」。
- `--drop-missing`：重新生成时删掉旧页面里有、新数据里没有的条目（默认拒绝，见下面生成规则）。
- `--page-id <身份号>`：只在新建页面时有用，沿用指定的身份号（例如旧页面坏了移走后重建，想让原来的固定网址继续能用）；身份号只能用字母、数字、`_`、`-`，4 到 64 位；根目录下已有这个身份号的文件就拒绝，所以要能找到根目录（`--root` 等，见下）。目标文件已存在时是重新生成，沿用旧页面的身份号，给了不同的 `--page-id` 就拒绝。

成功时打印「已生成创作页」或「已重新生成」、页面身份号、段数、建议条数（有删句建议时写「M 条建议（其中 K 条是删掉这句）」）和服务地址；「提醒：」开头的行是不拒绝、但要看的问题。

输入数据（三方共同遵守）：

```json
{
  "content_id": "T001", "type": "口播", "stage": "写稿", "title": "…",
  "narrative": { "story": "讲了个什么故事", "audience": "给谁看", "problem": "解决什么问题" },
  "speech_rate": 5, "service_origin": "http://127.0.0.1:18977",
  "segments": [ { "id": "可选，已有则沿用", "title": "…", "role": "这段起什么作用",
      "refs": [ { "who": "博主甲", "source_type": "口播原话", "time": "0:00 起", "text": "…", "url": "…" } ],
      "baseline": "…", "mine": "…", "note": "…",
      "locked": { "可选：额外的锁定键": "…" }, "fields": { "可选：额外的可改字段": "" } } ],
  "suggestions": [ { "id": "可选", "segment": "段落 id 或段落在数组中的序号（从 1 起）", "category": "衔接", "source": "AI",
      "original": "…", "proposed": "…（删掉整句时写空字符串）", "reason": "…", "basis": { "type": "AI 自己的判断", "text": "…" }, "verdict": "待你定",
      "locked": { }, "fields": { } } ],
  "info": { "locked": { "可选：页面信息的额外锁定键": "…" }, "fields": { "可选：页面信息的额外可改字段": "" } },
  "items": [ { "id": "可选", "kind": "step", "locked": { "segment": 1, "…": "…" }, "fields": { "prompt": "…" } } ]
}
```

`segments`、`suggestions` 里的 `locked`、`fields` 和顶层的 `info`、`items` 都是可选的，用来放「只加不删」的扩展：`locked`、`fields` 原样并进这个条目；`items` 放新种类的条目，按顺序排在建议后面。参考里的额外键直接写在参考里。

校验（不合格就拒绝生成，一次列出全部原因）：

- 必填：`content_id`、`type`、`stage`、`title`、`segments`（至少一段）；每段必填 `title`、`mine`（可以是空字符串，但必须有）；每条参考必填 `source_type`、`text`，除 `说明` 以外还必填 `who`。`type` 是 `口播` 时 `narrative` 的三项都不能空。`说明` 带了 `time` 或 `url` 只提醒（页面上不显示）。
- 取值：`type`、`stage`、`source_type`、`category`、`source`、`basis.type`、`verdict` 必须是上表里的值；`speech_rate` 是正数，默认 5；`service_origin` 必须是 `http://127.0.0.1:端口`，默认是工作台设置里保存服务的端口（`http://127.0.0.1:18977`）；参考的 `url` 为空或以 `http://`、`https://` 开头。
- 身份号：格式见上；所有条目的 id 不重复。
- 建议：`segment` 写段落 id，或段落在 `segments` 数组里的序号（从 1 起，数字或数字字符串都行），生成时换成段落 id；`original`、`reason` 不能空；`proposed` 必须有、必须是文字（空字符串表示删掉整句，见第二节「删句建议」）；`original` 在所属段 `mine` 里恰好出现一次。
- 扩展：`locked`、`fields` 必须是对象，可改字段的值必须是字符串，键不能和这种条目的固定键重名（固定键写在外层），`locked` 里不能写 `ai_state`；`items` 里每条的 `kind` 用小写字母开头、只含小写字母数字下划线，不能是 `info`、`segment`、`suggestion`（这三种写在各自的地方）；条目的 `locked.segment` 一律指所属段落，写段落 id 或段序号，找不到就拒绝。
- 除了上面这些扩展位置，别处不认识的键不报错，但会打印「没用上」的提醒，免得拼错键名悄悄丢数据。

生成规则：

- 没有 id 的条目生成随机短码；段落的 `order` 按数组顺序从 1 起。
- 目标文件不存在：原子地新建（不会盖掉同时出现的同名文件）；要沿用指定的身份号见上面的 `--page-id`。
- 目标文件已存在（重新生成）：在页面锁里读旧 jc-doc，沿用 `page_id`、`token`；页面信息条目沿用旧 id；按身份号保留旧条目的全部可改字段（`mine`、`note`、`proposed`、`decision`、`overall_note`、`approved`、`recorded`，以及扩展出来的字段）和 `locked.ai_state`，输入里这几格的值不用（和旧值不同时打印提醒）；旧条目有、新数据没写的可改字段也接回来。建议原句的「恰好一次」按保留下来的 `mine` 查：新建议不满足就拒绝；已有建议不满足只提醒（用户可能已经采纳或改过那句）。旧页面里有、新数据里没有的条目会被删掉，默认拒绝并列出来，确认要删时加 `--drop-missing`。写入走保存服务同一套「临时文件、替换前核对、写前留版本、写后回读」。
- 旧文件读不出 jc-doc，或旧页面的 `content_id` 和数据不一样：拒绝（多半是路径写错了）。
- 页面锁放在工作文件夹的 `.jc-locks/` 下。根目录（工作文件夹）按这个顺序找：`--root`；环境变量 `JC_BRAIN_ROOT`；工作台设置文件里的 `workFolder`（页面文件在它下面时）；页面 `service_origin` 上正在运行的保存服务报告的根目录（页面文件在它下面时）；从页面文件往上找带 `.jc-locks` 的目录。重新生成时都找不到就拒绝，请加 `--root`。

### 读和改：`brain_page.py`

`<页面>` 可以是页面文件路径、page_id，或内容编号（例如 `T001`，根目录下只有一个这样的创作页时）；后两种需要能找到根目录。条目用身份号指定，页面信息条目也可以写 `info`。

| 命令 | 做什么 |
| --- | --- |
| `read <页面>` | 打印给 AI 读的摘要：页面信息、叙事、整体意见、「内容已确认」、每段当前我的版本、和底稿比的删改（CriticMarkup：`{--删掉的--}`、`{++加上的++}`、`{~~原来~>现在~~}`）、待处理的写给 AI 的话、各建议的决定和原句还对不对得上（删句建议的「改成」写成「删掉这句」）、录完的定稿；扩展出来的格子和新种类的条目列在各段下面和「其他格子和条目」里 |
| `export <页面> [--out 文件]` | 把现有页面导出成 `build_page.py` 的输入数据（带全部身份号和全部扩展），用来改完再重新生成 |
| `reply <页面> --item <段id> --text <回复>` | 把这一段当前的 `note` 抄进 `ai_state.handled_note`，写 `ai_state.reply` 和 `replied_at`（不改指纹）。`--item info` 时回复的是整体意见 `overall_note` |
| `suggest <页面> --segment <段id> --category … --original … --proposed … --reason … --basis-type … [--basis …] [--source AI] [--verdict 待你定] [--id …]` | 新增一条建议，检查原句在该段当前 `mine` 里恰好出现一次。删掉整句写 `--proposed ''` |
| `set-locked <页面> --item <id> --key <键> --value <值> [--json]` | 改锁定字段（例如页面信息的 `stage`、`narrative`）；`--json` 表示值按 JSON 解析。不能改 `ai_state`（用 `reply`）。改建议的 `original` 时，新原句必须在所属段当前 `mine` 里恰好出现一次，否则拒绝；改建议的 `segment` 时，原句必须在新段里恰好出现一次 |
| `set-field <页面> --item <id> --field <字段> --value <值> [--before <改前值>] [--user-approved]` | 改可改字段，走和页面一样的逐格规则并记进改动记录。`mine`、`note`、`decision`、`overall_note`、`approved` 没有 `--user-approved` 一律拒绝 |
| `rebase <页面> (--item <段id> … / --all)` | 把当前 `mine` 抄成 `baseline`（AI 交新稿、用户认可后用）。`baseline` 在指纹里，所以用户这时正在改的这一段会按冲突处理 |
| `publish <页面> --file <文件>` | 一次放进标题、封面文字、简介的候选（只加不删，见第二节「发布文字」） |
| `list` | 列出根目录下所有带 jc-doc 的页面 |

文字参数（`--text`、`--original`、`--proposed`、`--reason`、`--basis`、`--value`、`--before`）写成 `-` 时从标准输入读，末尾的换行会去掉（heredoc、`echo` 都会多带一个；和 `"$(cat 文件)"` 一样），中间的换行保留。标准输入只能读一次，一条命令里第二个写成 `-` 的参数直接拒绝，不会悄悄读到空。`brain_page.py -h` 和各子命令的 `-h` 里也写着这条。

所有改动都在页面锁里重读、修改、原子替换，替换前发现文件被动过就重来；同一个 page_id 有多份文件时拒绝（不按顺序挑一份）；给的文件不是保存服务认的那份（例如工作文件夹以外的副本）也拒绝。`set-field` 的改动和页面上的改动一样记进 `.jc-changes/<page_id>.jsonl`，来源写 `brain_page`；改锁定字段不进改动记录（改动记录只记格子），但写前的旧文件照样留在 `.jc-versions`。成功退出码 0，拒绝或失败退出码 1，原因写在标准错误里。

保存服务状态：`python3 where.py` 会说保存服务在不在、端口是多少、根目录对不对得上。

## 五、保存服务接口（`server/brain_save.py`）

保存服务只做通用的逐格规则，不认识「创作页」。新页面类型只改模板，不改服务。

启动：平时由工作台的 `pnpm start` 一起拉起（根目录取设置里的工作文件夹，回收站不扫）。单独运行：`python3 server/brain_save.py --root <工作文件夹> [--port 18977] [--skip-dir <不扫的文件夹>] [--template-dir <目录>] [--kit-dir <目录>] [--read-only]`，只听本机回环地址：`127.0.0.1` 和 `::1` 的同一端口（原因见下面「来源隔离」）。模板目录默认是服务文件旁的 `../template`（放 `style.css`、`app.js`），kit 目录默认是 `../kit`（放 `kit.js`）。`--read-only` 起的是预览用的只读实例：所有写入请求一律 403，不写任何文件（没有锁、版本、改动记录），`/p/` 页面顶上加一条黄色横幅说明改动不会存回文件。端口被别的程序占着时不启动，退出码 3，日志说清是谁占着。

### 来源隔离：两个主机名

浏览器按「协议 + 主机名 + 端口」区分来源，`127.0.0.1` 和 `localhost` 是两个来源，一个来源里的脚本读不到另一个来源的回答（除非对方的回答里明确放行）。`/f/` 提供的没接入同步的页面谁写的都有（AI 生成的报告、下载来的网页），它们的脚本不能碰到能存回文件的创作页，所以两类页面分在两个主机名上：

| 地址 | 提供什么 | 用另一个主机名访问时 |
| --- | --- | --- |
| `http://127.0.0.1:端口` | `/p/` 页面、`/p/…/meta`、`/p/…/doc`、`/p/…/changes`、`POST /save`（以及它的预检 `OPTIONS`） | 用 localhost 访问这些一律 403；在浏览器里打开 `/p/<page_id>` 时给一页人话，附 127.0.0.1 的地址 |
| `http://localhost:端口` | 只有 `/f/` | 用 127.0.0.1 访问 `/f/` 会 302 到 localhost 的同一路径（编码和查询串原样） |
| 两个都行 | `/healthz` | |

- 别的 Host（例如把别的域名解析到本机、`[::1]:端口`、不带端口）一律 403。
- `POST /save` 的 Origin 只认 `http://127.0.0.1:端口`，和带口令的 `null`（直接打开的 file:// 页面）；`http://localhost:端口` 等其他来源一律 403。`/doc` 含口令，不给任何跨源页面读；`/meta`、`/changes` 只给 `http://127.0.0.1:端口` 和 `null` 读（不含口令）。所以 localhost 上的页面拿不到口令，也就写不进任何格子。还剩一个口子要知道：沙箱框架里的脚本来源也是 `null`，任何网页都能借它读 `/meta` 和 `/changes`（改动记录里有改前改后的文字），但前提是知道页面身份号，而且读不到口令、写不进去。
- `/f/` 打开的是接入同步的页面时，302 到 `http://127.0.0.1:端口/p/<page_id>`（完整地址，不是相对路径）。
- 工作台给创作页的地址是 `http://127.0.0.1:端口/p/<page_id>`（`lib/works.mjs`，端口是这次 `pnpm start` 实际给保存服务的端口）。
- `localhost` 在 macOS 上可能先解析到 IPv6 的 `::1`，所以服务在 `127.0.0.1` 和 `::1` 的同一端口上各听一个，两边规则完全一样。`::1` 上这个端口被别的程序占着时服务不启动（退出码 3，日志写「[::1]:端口 端口已被别的进程占用」），否则 localhost 可能连到那个程序上；本机开不了 `::1`（没有 IPv6）时只听 `127.0.0.1`，原因写进启动日志和 `/healthz` 的 `listen_problem`，这时 localhost 也只会解析到 `127.0.0.1`。
- 同一个页面在两个来源下的浏览器存储是分开的：以前用 127.0.0.1 打开 `/f/` 页面时存在浏览器里的东西，换到 localhost 后看不到（文件本身不受影响）。

这套隔离由 `tests/test_files.py` 的 `HostIsolationTests`、`Ipv6BusyTests` 和浏览器场景 `isolation`（`tests/browser/scenarios.mjs`，无头 Chrome 里真的从 localhost 页面发请求）验证。

### 接口

| 接口 | 主机名 | 说明 |
| --- | --- | --- |
| `GET /healthz` | 两个都行 | `{service, protocol: 1, features: ["group", "changes", "template", "files"], pid, started_at, root, root_ok, writable, read_only, duplicates, kit_path, template_dir, origin, files_origin, listen, listen_problem, kit_ok, kit_problem, style_ok, style_problem, app_ok, app_problem}`。`origin` 是 `/p/` 和保存的地址，`files_origin` 是 `/f/` 的地址，`listen` 是实际在听的回环地址（正常是 `["127.0.0.1", "::1"]`）；`*_ok` 为 false 时页面这一段改用自带的，原因在 `*_problem`。本机任意端口的页面都能跨源读（工作台打开页面前先问服务在不在） |
| `GET /p/<page_id>` | 127.0.0.1 | 页面本身（kit、样式、界面脚本都换成当前模板，见第一节） |
| `GET /p/<page_id>/meta[?file=<绝对路径>]` | 127.0.0.1 | `{fingerprint, path[, same_file]}`，file:// 页面也能读 |
| `GET /p/<page_id>/doc` | 127.0.0.1 | `{fingerprint, path, doc}`，含口令，不给任何跨源页面读 |
| `GET /p/<page_id>/changes[?item=<条目id>]` | 127.0.0.1 | `{changes: [{time, change_id, item, field, before, after, origin[, group]}]}`，按时间正序；不带 item 返回全部。file:// 页面也能读 |
| `GET /f/<相对根目录的路径>` | localhost | 只读提供根目录下的文件：网页、图片、样式、脚本、文字、表格、音视频、字体和 PDF，页面里的相对链接照常能用，视频能拖进度条（单段 Range）。以 `.` 开头的目录（回收站、版本备份等）、`node_modules`、根目录以外（包括快捷方式指出去的）、不在类型表里的文件（`.py`、`.env` 等）一律不给。接入同步的页面 302 到固定网址；页面脚本用了浏览器存储、或者有可以输入内容的地方时，页面顶上加一条黄色横幅，说明改动只会留在这个浏览器里（文件本身不动） |
| `POST /save` | 127.0.0.1 | 见下 |

`POST /save` 请求体：

```json
{ "page_id": "…", "token": "…", "self_path": "file:// 打开时自己的绝对路径（可选）",
  "changes": [ { "change_id": "…", "item_id": "…", "field": "mine", "before": "改前值", "after": "改后值", "item_fp": "条目指纹", "group": "可选" } ] }
```

逐格规则：条目没了是 `item_gone`；指纹不对是 `item_changed`；字段没了是 `field_gone`；文件里已经是改后值是 `ok/already`；文件里等于改前值就写入 `ok/written`；都不是是 `changed`。比较前统一换行符和 NFC。冲突时结果里带 `current`（文件里现在的值）。

`group`：同一请求里 `group` 相同的改动全成或全不成。先逐条判断，组里只要有一条冲突，整组都不写，整组每条都返回 `status: "conflict"`：自己就冲突的那条带自己的原因；本来能写的那几条原因是 `group_conflict`，带 `group`、`current` 和 `item_fp`。不同组、不带组的改动互不影响。组只在一次请求里有效。

改动记录：每写入一格，往 `<根目录>/.jc-changes/<page_id>.jsonl` 追加一行 `{time, change_id, item, field, before, after, origin[, group]}`；`origin` 是页面来源（`http://127.0.0.1:端口` 或 `null`），AI 命令写的是 `brain_page`。写入前把旧文件存进 `<根目录>/.jc-versions/<page_id>/`，保留最近 20 版。
