# 评论洞察怎么做

这份说明写给分析评论区的 AI。目的只有一个：读完一条视频的评论，告诉用户写视频时能直接用的东西。方法是用户研究里常用的归类做法（先逐条看、给每条贴一个「在说什么」的短标签，再把意思相近的合成一类，有人叫它亲和图），不套任何课程或付费方法里的固定框架和术语。

分工：AI 读懂评论、归类、写结论和选题；程序（`research.py comments render`）算条数、点赞、属地，核对引用，出报告。AI 只写评论的短号（c1、c2……），不写数字。

## 一、先读完

- 用 `comments show` 把全部有效评论读完，一次 300 条，按提示接着看。不抽样，不只看点赞高的：低赞但具体的问题，常常就是下一条视频。
- 读的时候顺手记：有人在问什么、卡在哪、想用在哪、用了以后怎样、在夸还是在骂、要什么资料。
- 清单里标着「回复cN」的是楼中楼，回复的是 cN；标「作者」的是视频作者本人的回复。作者已经回答过的问题，结论里要说「作者在评论里回答过」。

## 二、归类

先给每条有内容的评论贴一个短标签，再把意思相近的标签合成一类。每一类：

- **name**：用评论者自己的话起名，看一眼就知道是什么事。「录音导不进去」比「导入问题」好，「怕公司开会内容泄露」比「隐私顾虑」好。20 字以内。
- **kind**：六选一。
  - 需求：想要什么、想用在什么场景（「上课也能这样整理吗」）。
  - 痛点：卡在哪、哪里不满意、担心什么（「方言识别不了」「怕不安全」）。
  - 疑问：一个具体的问题（「免费能用多久」）。
  - 反馈：用了以后怎样，夸或者吐槽（「试了，真的三分钟就好」）。
  - 求资料：要链接、模板、教程、口令。
  - 其他：放不进上面几类、但值得单独看的。
- **comments**：这一类包括哪几条（评论短号）。一条评论可以进几类。闲聊、@朋友、单纯夸一句的，可以哪类都不进。
- **summary**：一句话说这一类人具体在说什么，160 字以内。
- **quotes**：挑 1 到 3 条代表原话。优先具体、有场景、说出了原因的，不只挑点赞最高的。长评论只想摘其中一句，写成 `{"ref": "c12", "excerpt": "摘的那一句"}`，摘的字必须和原文一字不差。

几条经验：

- 「求资料」「求链接」「扣 1」单独成一类。它说明有人想要，但不说明这件事难；不要拿它的条数去证明「大家很需要」。
- 一类占了三分之一以上，多半混了几件事，再拆开看。只有一两条的类，能并就并，并不了就留着，报告会标「只是线索」。
- 同一句话被很多人重复（比如都在问同一个问题），是信号，照常计数；同一个人刷屏的，按一条算更稳妥，在 caveats 里说一声。

## 三、写给第一屏的东西

报告第一屏只有两样：结论和能直接拍的选题。用户最不想看的，是一屏图表和一堆没结论的分类。

**结论（takeaways，3 到 5 条）**：每条一句话，回答「这对写视频意味着什么」。常见的几种：

- 哪件事最多人卡住（原视频没讲清、或者没讲到的步骤）。
- 大家最想用在什么场景（下一条视频的切入口）。
- 最多人担心什么（视频里要提前回答的顾虑）。
- 评论里有、原视频完全没碰的话题。

每条都写依据：`categories` 写分类 id，或者 `evidence` 写几条评论的短号。差的写法：「观众对这个工具很感兴趣」——回不到证据，也没法用。好的写法：「最多人卡在第一步：手机里的录音导不进去」——有对象，有依据，能直接变成一条视频。

**选题（topics，1 到 5 个）**：从痛点、疑问、需求里长出来。

- **title**：像一条视频的标题，具体到能拍。
- **why**：为什么值得拍，说依据（「评论里问导入的最多，原视频只用一句话带过」）。
- **audience**：拍给谁，用评论里出现的人（「刚装好、第一次用的人」「要整理课堂录音的学生」）。
- **categories** 或 **evidence**：依据是哪几类、哪几条。

## 四、评论的都是谁（人群画像）

- 只用评论里自己说出来的身份和处境：「我是做行政的」「我们开会都说粤语」「上课录音」。一组写清是哪几条（`comments`）。
- 不猜年龄、性别、收入、学历这些评论没说的。没人说自己是谁，就只写 summary，不硬分组。
- IP 属地程序会自动算前几名，不用写。属地只说明评论时人在哪个省。

## 五、样本够不够

程序会给每一类、每个选题标上：10 条以上「够看出方向」，4 到 9 条「有一些，还要再看」，3 条以下「很少，只是线索」；有效评论不到 30 条，整份报告顶上会写「只当方向参考」。

AI 自己觉得要提醒的，写进 `caveats`（一句一条）：比如评论大多是发布第一天的、某一类像是刷的、只采了一级评论没看楼中楼、平台显示的评论比这次拿到的多很多。

## 六、不做的事

- 不推断付费意愿、购买力（没有交易数据）。
- 不把点赞数说成人数：点赞说明有多少人认同这句话。
- 不写读心的话：「他们真正想要的是……」「本质上是焦虑」。写评论里说出来的。
- 不改评论原文，不替评论者润色，错别字也照抄。

## 分析.json 的格式

放在报告文件夹里，和 `评论数据.json` 在一起：

```json
{
  "title": "会议纪要教程的评论区：录音导入和收费最让人卡住",
  "takeaways": [
    {"text": "最多人卡在第一步：手机里的录音导不进去", "categories": ["import"]},
    {"text": "一半人在问要不要钱、免费能用多久，视频里一句没提", "categories": ["price"], "evidence": ["c31"]}
  ],
  "topics": [
    {"title": "手机录音、微信语音、会议软件录音，三种怎么导进去", "why": "问导入的评论最多，原视频只用一句话带过",
     "audience": "刚装好、第一次用的人", "categories": ["import"]}
  ],
  "categories": [
    {"id": "import", "name": "录音导不进去", "kind": "痛点", "summary": "装好以后不知道手机录音、微信语音怎么导进去",
     "comments": ["c1", "c2", "c17"], "quotes": ["c1", {"ref": "c17", "excerpt": "微信里的语音怎么弄进去"}]},
    {"id": "price", "name": "要不要钱", "kind": "疑问", "summary": "问收费、免费额度够不够用", "comments": ["c3", "c31"]}
  ],
  "persona": {
    "summary": "大多是要开会做记录的上班族，也有学生想整理课堂录音",
    "groups": [{"name": "说自己开会说方言的", "description": "担心方言识别不准", "comments": ["c5", "c40"]}]
  },
  "caveats": ["只采了一级评论，楼中楼里的追问没看到"]
}
```

- `title` 40 字以内，说清这份报告最重要的发现。
- `takeaways`、`topics`、`categories` 都至少一条；`persona`、`caveats` 可以不写。
- 写完运行 `comments render`。它报的问题照着改；「提醒：」开头的看一眼，确实没问题就不用管。
